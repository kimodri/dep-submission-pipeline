# Lesson 4: Source Data and Extraction Metadata

## Why this matters

An extracted payload is not enough to explain itself.

Later stages also need to know which pipeline run captured it and when that
capture happened. If the payload and its metadata travel separately, they can
be mismatched, regenerated at the wrong time, or forgotten during a replay.

This lesson develops one small boundary object:

```python
@dataclass(frozen=True)
class Extraction:
    run_id: str
    extracted_at: datetime
    payload: dict[str, Any]
```

The goal is not merely to learn dataclass syntax. The goal is to understand:

- which values came from the source;
- which values were generated by the pipeline;
- which function creates each value;
- how arguments enter a function;
- how a dataclass instance returns from a function;
- how later stages keep the payload attached to its metadata.

## Starting point in the code

The relevant structure is:

```text
src/
└── pipeline/
    ├── __main__.py
    ├── database.py
    └── etl/
        ├── extract.py
        ├── bronze.py
        ├── silver.py
        └── load.py
```

The intended responsibilities are:

```text
__main__.py
└── creates the identity of one pipeline run and coordinates the stages

extract.py
└── calls the source and returns the payload with extraction metadata

bronze.py / load.py
└── persists and retrieves the extraction

silver.py
└── transforms a retrieved extraction into typed records
```

The examples below use neutral placeholder operations such as
`request_source()`, `serialize()`, `deserialize()`, and `transform_payload()`
to keep attention on argument flow. They are not Python or DuckDB built-ins and
would need concrete implementations in an application.

## Realization 1: Source data and pipeline metadata describe different things

### Initial belief

> All values needed by a transformation are simply columns in the data.

### Why it seemed reasonable

The source response already contains identifiers, timestamps, names, and other
fields. Adding another timestamp during DataFrame creation can look like an
ordinary transformation step.

The missing distinction is the event that each value describes.

### Source data

Source data is supplied by the external system:

```text
record identifier
record title
source creation time
source update time
nested source attributes
```

For example:

```python
payload = response.json()
```

The decoded `payload` represents what the source returned.

### Pipeline metadata

Pipeline metadata is generated by the pipeline to describe its own work:

```text
run_id
extracted_at
```

These fields answer different questions:

| Value | Question answered |
|---|---|
| `payload` | What did the source return? |
| `run_id` | Which logical pipeline run captured it? |
| `extracted_at` | When did this pipeline observe it? |

A source `updated_at` value is not a replacement for `extracted_at`:

```text
source updated_at
└── when the record changed in the source

pipeline extracted_at
└── when this pipeline observed the response
```

### Evidence from replay

Suppose data is extracted on Monday and transformed again on Thursday.

If the transformation generates a new `extracted_at`, the stored record will
claim it was extracted on Thursday. That is historically false: Thursday was
the transformation time, not the extraction time.

```text
Monday
├── source response received
└── extracted_at must be recorded here

Thursday
├── stored response replayed
└── original extracted_at must be reused
```

### Revised mental model

> Generate metadata at the event it describes, then preserve it when the data
> crosses later boundaries.

The entry point creates the run identity because the run covers the complete
pipeline. The extractor records the extraction time because it knows when the
response was received.

## Realization 2: A dataclass keeps related values in one boundary object

Passing three independent values is possible:

```python
load_raw_bronze(
    connection,
    run_id,
    extracted_at,
    payload,
)
```

But every caller must remember which values belong together. A dataclass gives
that group a name and a visible structure:

```python
from dataclasses import dataclass
from datetime import datetime, timezone
from typing import Any


@dataclass(frozen=True)
class Extraction:
    run_id: str
    extracted_at: datetime
    payload: dict[str, Any]
```

This says that one extraction contains exactly these three attributes.

### What the annotations mean

```python
run_id: str
```

The run identifier should be a string.

```python
extracted_at: datetime
```

The extraction time should be a `datetime` value.

```python
payload: dict[str, Any]
```

The top level is a dictionary with string keys. `Any` is used because decoded
JSON can contain several nested value types:

```text
string
number
boolean
null
list
dictionary
```

The annotations document the intended contract and help type-checking tools.
Python does not automatically perform complete runtime validation merely
because annotations are present.

### What `@dataclass` generates

The decorator generates ordinary class behavior such as an initializer. This
allows an instance to be created with:

```python
extraction = Extraction(
    run_id="example-run",
    extracted_at=observed_at,
    payload=source_payload,
)
```

Without a dataclass, a similar class would need a manually written
`__init__()` method.

### What `frozen=True` means

It prevents rebinding an attribute after construction:

```python
extraction.run_id = "different-run"  # raises an error
```

This is useful because extraction identity should not change while the object
travels through the pipeline.

It is only shallow protection. The nested dictionary is still mutable:

```python
extraction.payload["new_key"] = "new value"
```

The dataclass keeps the envelope stable; it does not recursively freeze every
object stored inside it.

## Realization 3: A function call and dataclass instantiation are different

Consider:

```python
extraction = extract_source(...)
```

This is a function call. It is not direct dataclass instantiation.

The function can instantiate the dataclass internally:

```python
def extract_source(run_id: str) -> Extraction:
    response = request_source()
    source_payload = response.json()
    observed_at = datetime.now(timezone.utc)

    return Extraction(
        run_id=run_id,
        extracted_at=observed_at,
        payload=source_payload,
    )
```

The two operations are:

```python
extract_source(...)
# Call a function.
```

```python
Extraction(...)
# Instantiate a class and create an Extraction object.
```

### Execution trace

```text
Call extract_source(...)
    ↓
Enter the function
    ↓
Call the source
    ↓
Decode the payload
    ↓
Instantiate Extraction(...)
    ↓
Return the Extraction instance
    ↓
Assign that instance to the variable named extraction
```

After the assignment:

```python
extraction = extract_source(...)
```

the variable `extraction` refers to the returned instance:

```python
extraction.run_id
extraction.extracted_at
extraction.payload
```

### Class, instance, function, and variable

| Expression | Meaning |
|---|---|
| `Extraction` | The class definition |
| `Extraction(...)` | Creating an instance of the class |
| `extract_source` | The function object |
| `extract_source(...)` | Calling the function |
| `extraction` | A variable referring to the returned instance |

## Realization 4: Arguments move values across function boundaries

The entry point creates one run identity:

```python
def main() -> None:
    run_id = create_run_id()

    extraction = extract_source(
        run_id=run_id,
    )
```

This line contains two different uses of the same name:

```python
run_id=run_id
```

The left side is the parameter being supplied:

```text
run_id=
```

The right side is the local value in `main()`:

```text
=run_id
```

Using different names makes the movement easier to see:

```python
pipeline_run_id = create_run_id()

extraction = extract_source(
    run_id=pipeline_run_id,
)
```

The call maps:

```text
main() local variable       extract_source() parameter
pipeline_run_id       ───>  run_id
```

Inside the function, the parameter is used while constructing the return
value:

```python
return Extraction(
    run_id=run_id,
    extracted_at=observed_at,
    payload=source_payload,
)
```

The complete value flow is:

```text
main() creates pipeline_run_id
    ↓ passes it as run_id
extract_source(run_id)
    ↓ combines it with extracted_at and payload
Extraction instance
    ↓ returned to main()
extraction variable
```

### Why the extractor does not create the run ID

The extraction is only one stage of the run:

```text
pipeline run
├── extraction
├── Bronze load
├── Silver transformation
└── Gold transformation
```

If every stage generated its own run ID, related records would appear to come
from different runs. The coordinator creates the ID once and passes it through
the stages that need it.

## Realization 5: Pass the extraction object to keep context attached

A loader can accept the complete object:

```python
def load_raw_bronze(
    connection,
    extraction: Extraction,
) -> None:
    connection.execute(
        """
        INSERT INTO bronze.raw_extractions (
            run_id,
            extracted_at,
            raw_response
        )
        VALUES (?, ?, ?)
        """,
        [
            extraction.run_id,
            extraction.extracted_at,
            serialize(extraction.payload),
        ],
    )
```

The call is compact:

```python
load_raw_bronze(
    connection,
    extraction,
)
```

The loader receives one object whose attributes already belong together.

This is preferable to reconstructing metadata inside the loader:

```python
def load_raw_bronze(connection, payload):
    run_id = create_run_id()       # wrong ownership
    extracted_at = current_time()  # wrong event time
```

The loader did not start the run and did not observe the source response, so it
should not invent either value.

## Retrieving the same boundary object from Bronze

Silver should be reproducible from persisted Bronze. A database reader can
retrieve one run and reconstruct the same kind of object:

```python
def get_raw_extraction(
    connection,
    run_id: str,
) -> Extraction:
    row = connection.execute(
        """
        SELECT
            b.run_id,
            b.extracted_at,
            b.raw_response
        FROM bronze.raw_extractions AS b
        WHERE b.run_id = ?
        """,
        [run_id],
    ).fetchone()

    if row is None:
        raise ValueError("Extraction was not found")

    return Extraction(
        run_id=row[0],
        extracted_at=row[1],
        payload=deserialize(row[2]),
    )
```

The parameter placeholder is important:

```sql
WHERE b.run_id = ?
```

The `?` receives the Python value supplied in:

```python
[run_id]
```

This is different from:

```sql
WHERE run_id = run_id
```

which compares a column with itself instead of selecting the requested run.

## Pure transformation after the database read

The stage coordinator needs a connection because it reads and writes database
tables:

```python
def run_silver(connection, run_id: str) -> None:
    extraction = get_raw_extraction(
        connection,
        run_id,
    )

    silver_data = transform_raw_to_silver(
        extraction,
    )

    load_silver(
        connection,
        silver_data,
    )
```

The transformation itself does not need a connection:

```python
def transform_raw_to_silver(
    extraction: Extraction,
) -> pd.DataFrame:
    payload = extraction.payload

    result = transform_payload(payload)
    result["run_id"] = extraction.run_id
    result["extracted_at"] = extraction.extracted_at

    return result
```

The database query already happened in `get_raw_extraction()`. At the moment
`transform_raw_to_silver()` is called, the payload and metadata are ordinary
in-memory Python values.

This separation produces three clear operations:

```text
get_raw_extraction()
└── database read

transform_raw_to_silver()
└── pure Python or Pandas transformation

load_silver()
└── database write
```

## Resulting architecture

```text
__main__.py
│
├── create run_id
│
├── call extract_source(run_id=run_id)
│       └── return Extraction instance
│
└── open database connection
        │
        ├── load_raw_bronze(connection, extraction)
        │
        └── run_silver(connection, run_id)
                │
                ├── get_raw_extraction(connection, run_id)
                │       └── return Extraction instance
                │
                ├── transform_raw_to_silver(extraction)
                │       └── return DataFrame
                │
                └── load_silver(connection, DataFrame)
```

The data moves through several representations, but its identity remains
attached:

```text
source response
    ↓
Extraction(run_id, extracted_at, payload)
    ↓
Bronze row
    ↓
Extraction(run_id, extracted_at, payload)
    ↓
Silver records carrying run_id and extracted_at
```

## Reusable decision rules

- Separate source values from metadata generated by the pipeline.
- Generate a timestamp at the event it actually describes.
- Create a logical run ID once and pass it through related stages.
- Use a dataclass when several related values repeatedly cross function
  boundaries together.
- Distinguish calling a function from instantiating the object it returns.
- Pass values explicitly instead of regenerating them in lower-level
  functions.
- Let database readers reconstruct a meaningful boundary object instead of
  returning an unexplained tuple to every caller.
- Keep transformation functions independent of the database when they only
  need in-memory input.

## Questions to ask in a future project

1. Did this value come from the source or from the pipeline?
2. Which event does this timestamp describe?
3. Which component owns the identity of the complete run?
4. Are related arguments repeatedly passed separately when they should form
   one named object?
5. Is this expression calling a function or instantiating a class?
6. After replay, will the data retain its original extraction metadata?
7. Has the database query already happened before the pure transformation is
   called?
8. Can the transformation be tested using an `Extraction` instance without a
   live database?
